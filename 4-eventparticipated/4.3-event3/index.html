First Cloud AI Journey: Community Day

First Cloud AI Journey: Community Day

Event Information

  • Date: Saturday, October 31, 2026
  • Location: Bitexco Financial Tower, Ho Chi Minh City
  • Organizer: AWS Study Group / First Cloud AI Journey (FCAJ) community
  • Role: Attendee
  • Format: Six morning sessions by industry speakers and FCAJ interns

Event Overview

Community Day brought together the First Cloud AI Journey community, where working engineers and program interns shared hands-on experience with AWS. Unlike the two previous events, the agenda did not focus on a single service or use case. It followed the path of a cloud learner: getting started with AWS, bringing AI into the software development process, building serverless applications, re-architecting web workloads, handling asynchronous processing, and contributing to open source.

Session 1 - AWS Roadmap for Beginners

Speaker: Minh Tuấn - Backend Developer, FCAJ intern

The opening session introduced a structured, low-cost path for beginners to learn AWS.

  • AWS Study Group: step-by-step hands-on labs in Vietnamese, regularly updated by community admins.
  • AWS Skill Builder: role-based learning plans, labs, and certification preparation, such as AWS Certified Cloud Practitioner.
  • AWS Builder Center: reading and writing technical articles, joining hackathons and Student Builder Groups.
  • AWS Cloud Quest: game-based 3D learning with free courses such as Cloud Practitioner and AI Foundations.
  • Student benefits: student verification for a Skill Builder Subscription (worth about $449/year) and certification vouchers earned through Builder Center badges; new accounts can also claim free credits.

The speaker stressed a safe lab workflow: understand the service → experiment → troubleshoot (ask AI or admins) → always clean up resources afterwards to avoid unexpected charges.

What I valued most was treating clean-up as a required step of every lab rather than an optional extra. It is a habit I need to keep when deploying personal projects on my own AWS account.

Session 2 - Lessons from Building a Software Factory with AI

Speaker: Henry Đức Bùi - Head of Engineering, CloudThinker

This session showed how a small team organizes its software delivery process around AI coding agents.

  • Results: a team of 5-6 people handled nearly 3,000 merge requests (MRs) in one month, about 100 per day, most of them executed and merged by AI.
  • The new bottleneck is people: once token budget is no longer the constraint, the limit becomes how many parallel agents humans can review and approve.
  • Discuss before coding: about 60% of the time goes to AI-assisted discussion, ending with HTML dashboards or diagrams generated by AI for the team to review and agree on.
  • Divergent prompting: avoid narrow prompts and leave room for the AI to suggest alternatives (for example, adding “feel free to advise me”).
  • “Folder Control” pattern: a single control folder with an agent.md file of basic instructions so agents can coordinate across multiple repositories and servers.
  • Automated review and merge: most small MRs, such as maintenance, refactoring, security checks, and performance tuning, are checked, debated, and merged by agents.
  • Verification by evidence: AI must run end-to-end tests and provide before/after screenshots or screen recordings of test runs.
  • CI/CD optimization: run CI on local or dedicated high-spec servers, cache test results (cutting test time by about 76%), and share dependency environments.

This session connected directly to the evidence over confidence principle from the Prove It series (Event 1): AI output is accepted only when backed by tests, screenshots, or recordings. I also realized that as AI writes code faster, reviewing, writing clear requirements, and designing verification steps become more important skills.

Session 3 - Three-Month Internship Journey: Building a Real-time Serverless Web Game

Speaker: Phúc Khang - FCAJ intern (Software Engineering)

The speaker presented a real-time multiplayer card game built during a three-month internship.

  • Tech stack: AWS Lambda, Amazon DynamoDB, Amazon SQS, Amazon EventBridge, Amazon API Gateway (WebSocket and HTTP), Amazon Cognito, AWS Amplify, and AWS CDK.
  • Four serverless patterns:
    • Synchronous: API Gateway + Lambda + DynamoDB for authentication and basic reads/writes.
    • Scheduled job: periodic leaderboard updates.
    • Asynchronous filtering: EventBridge for asynchronous event handling.
    • Message queue: SQS as a buffer for match results so the database is not overwhelmed when many results arrive at once.

Lessons from real incidents:

  • Using SQS as a turn timer caused polling between Lambda and SQS to generate about 863,000 requests with no players online, exceeding the Free Tier. The team switched to EventBridge as a “watchdog” for timeouts and AFK detection.
  • Do not put all permissions into a single IAM role, as it violates least privilege.
  • Do not store secrets directly in Lambda environment variables; use AWS Systems Manager Parameter Store or AWS Secrets Manager with AWS KMS.
  • Move from manual AWS Console changes to Infrastructure as Code with AWS CDK and AWS CloudFormation.

This was the session closest to my own situation as an intern. The 863,000-request incident showed that a service used for the wrong purpose can cost money even with zero users, and that budget alerts and metrics should be set up from day one, even for small projects.

Session 4 - Re-architecting Web Applications with AWS Lambda Web Adapter

Speaker: Thịnh Nguyễn - DevOps / Cloud Engineer, Style Solution

This session compared running web applications on traditional Lambda functions with packaging the whole web app as a container image and running it on Lambda through the Lambda Web Adapter.

Limitations of the traditional approach for web apps:

  • Each request occupies an execution environment, causing cold-start spikes during sudden traffic bursts.
  • Dependence on API Gateway adds latency and cost.
  • Billing includes time spent waiting for database I/O.

Proposed approach:

  • Package the web app (Express.js, FastAPI, …) as a Docker container image (up to 10 GB) and deploy it to Lambda.
  • According to the speaker, one execution environment can handle many concurrent requests (up to 128), so cold starts mainly affect the first request.
  • Route from Amazon CloudFront to a Lambda Function URL using Origin Access Control (OAC), without API Gateway and without exposing a public endpoint.
  • The speaker estimated a 40-70% reduction in compute cost because I/O wait time is not billed.

Selection criteria:

  • Traditional Lambda: small, single-purpose tasks such as generating S3 presigned URLs, sending notifications, or cron jobs.
  • Lambda with Web Adapter: full-stack web applications or complete API backends.

This session showed me that serverless does not require one function per route. For a .NET backend, I can consider packaging an entire ASP.NET Core API as a container image and compare the trade-offs with splitting it into separate functions.

Session 5 - Asynchronous Processing with Amazon SQS

Speaker: Cẩm Đào - FCAJ intern

This session explained why long-running tasks such as AI model calls should move from synchronous to asynchronous processing.

  • Synchronous: the user calls the API and waits until Amazon Bedrock finishes generating the result.
  • Asynchronous: the user submits a job → the API immediately returns a Pending status → the job is stored in SQS → an AI worker picks it up and processes it in the background.

Choosing a queue type:

  • Standard queue: very high throughput, but message order is not guaranteed.
  • FIFO queue: guaranteed ordering per message group ID, at lower throughput.

Safe message handling:

  • Visibility timeout and heartbeat: a received message is hidden for the visibility timeout; for long tasks, the consumer must extend it to prevent duplicate processing.
  • Long polling: set a wait time (for example, 20 seconds) when the queue is empty to reduce unnecessary requests and cost.
  • Dead-letter queue (DLQ): keep messages that exceed the retry limit for later inspection without blocking the main flow.
  • Fan-out with SNS + SQS: one message published to Amazon SNS is delivered to multiple SQS queues for logging or parallel processing.

This content applies directly to my logistics projects, where shipment events need asynchronous processing. I noted three checks for SQS: the visibility timeout must exceed processing time, a DLQ must be configured, and consumers must be idempotent because messages can be delivered more than once.

Session 6 - Staying Persistent: Open Source Contribution with AWS CDK

Speaker: Hưng Trần - Senior Cloud Engineer, NAB; Top 25 AWS CDK Contributor

The final session described the reality of contributing to large open-source projects such as Kubernetes, Terraform, and AWS CDK, where a pull request (PR) can take 6 to 8 months to be reviewed.

A three-stage contributor roadmap:

  • 0 → 1 PR: look for good first issue labels or join large refactoring campaigns where maintainers provide templates and checklists; keep PRs small and simple.
  • 1 → 20 PRs: try several repositories to find the project and maintainer team that fit best.
  • 20+ PRs: find your own work, for example by checking the AWS What’s New page daily and updating CDK, Terraform, or Pulumi when AWS launches a new feature or region.

Core mindset: spend about 15 minutes a day on small tasks such as version upgrades, and do not wait to read all documentation or understand the whole architecture before starting; the fastest way to learn is to fix a concrete issue.

This session changed how I see open source: it does not start with a large contribution but with consistency and patience. It is also a practical way to build a publicly verifiable portfolio.

Learning from the Speakers and Session Structure

What made Community Day different was that half of the speakers were interns. Intern sessions focused on concrete incidents, measurable numbers, and fixes, while industry speakers offered perspectives on process, cost, and long-term mindset. The two viewpoints complemented each other.

Presentation techniques I want to apply when sharing my own projects:

  • Tell real incidents with concrete numbers (requests, cost, time) instead of only describing an ideal architecture.
  • Show “before and after” when changing an architecture so the trade-offs are visible.
  • Give clear selection criteria (when to use A, when to use B) rather than presenting one solution as always right.
  • End with small actions the audience can take immediately.

Overall Learning Experience

The event helped me review the whole cloud learning journey from the perspective of people one step ahead. The sessions on serverless, Lambda Web Adapter, and SQS provided patterns I can apply to my current projects; the Software Factory session showed how AI is changing the way engineering teams work; and the sessions on open source and the beginner roadmap reminded me that progress comes from small, consistent actions.

After the event, I identified several items to practise: trying Lambda Web Adapter with a containerized .NET API, adding DLQs and tuning visibility timeouts for the queues in my projects, reviewing IAM roles and secret storage, and finding a good first issue in the AWS CDK repository to start contributing.

Key Takeaways

  • Always clean up resources and monitor cost when running labs or personal projects on AWS.
  • AI can greatly increase development throughput, but its output must be verified with tests and concrete evidence.
  • Choose services for the right purpose: misusing SQS can generate hundreds of thousands of unnecessary requests; EventBridge fits time-based monitoring better.
  • Apply least privilege to IAM, store secrets in Parameter Store or Secrets Manager, and manage infrastructure as code.
  • Lambda Web Adapter is worth considering for running a full web app on Lambda with lower cost and fewer cold starts.
  • Asynchronous processing with SQS needs a suitable visibility timeout, long polling, a DLQ, and idempotent consumers.
  • Open-source contribution starts with small PRs and requires months of persistence.
